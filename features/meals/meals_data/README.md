# meals_data

The data layer for meals. Implements `IMealsRepository` from
[`meals_domain`](../meals_domain).

Two data sources sit behind one repository: TheMealDB over HTTP, and a local Drift
database as a cache. Which one answers a given call is this package's business and
nobody else's.

## What lives here

| Path | Contents |
| --- | --- |
| `src/data_sources/mealdb_api_client/` | `MealDbApiClient`, `MealDbApiHttpException` |
| `src/data_sources/mealdb_api_client/dtos/` | `ApiMeal`, `SingleApiMealResponse` |
| `src/data_sources/meals_database/` | `MealsDatabase`, `meals.drift`, generated Drift code |
| `src/mappers/` | `ApiToDomainMealConverter`, `DbToDomainMealConverter` |
| `src/repositories/meals_repository.dart` | `MealsRepository` |

## How a read works

`MealsRepository` takes both data sources and both converters through its
constructor, so a test can supply fakes for any of them. A read checks the local
database first, falls back to the API, writes what it fetched back to the
database, and returns a domain `Meal` either way.

## DTOs never escape

`ApiMeal` is shaped like TheMealDB's JSON. `DbMeal` is generated by Drift and knows
about tables and columns. Neither is allowed past this package's boundary, because
a domain or presentation layer holding a Drift type would be coupled to Drift
forever.

Converters do the translating, and they are ordinary classes extending
`Converter<Input, Output>` from `dart:convert`:

```dart
class DbToDomainMealConverter extends Converter<DbMeal, Meal> { ... }
```

FFCA also allows extension methods or a generator like `auto_mappr`. Explicit
classes were chosen here because they can be injected and tested directly. They
live in `src/mappers/` and are **not** exported from the barrel: they are an
implementation detail of the repository, not part of this package's API.

## Public API

The barrel exports the repository and the data sources. The app needs both to
construct the repository; nothing outside needs the converters. `ApiMeal` is not
exported either: it is TheMealDB's wire shape, and a consumer that could name it
could bind to the api instead of to `Meal`.

## Who depends on this

Only [`mealify_app`](../../../apps/mealify_app), which constructs
`MealsRepository` and provides it as an `IMealsRepository`. No presentation layer
depends on this package. That is the rule that keeps the UI testable without a
database.

## Testing

`dart run melos test` from the repo root, or `fvm dart test` here. This is a pure
Dart package, so its tests use `package:test`.

The API client tests include integration tests that hit TheMealDB over the
network, so they can fail when it is unreachable.
