# mealify_app

The deployable app. Suggests a meal with a drink to match, and saves the pairs you
like.

In FFCA the app layer is thin by design. It builds no models, stores nothing, and
owns no screens. What it does own is composition: it constructs the concrete
repositories, defines the routing table, and decides what navigation means. It is
the only package that knows the full list of features.

## Running it

```sh
fvm flutter run \
  --flavor development \
  --target lib/main_development.dart
```

Three flavors, one entry point each: `main_development.dart`,
`main_staging.dart`, `main_production.dart`. Each calls `bootstrap()` with a
`MealifyApp`, and `bootstrap` installs the error handler and the `BlocObserver`
that every flavor shares.

## What lives here

```
lib/

  main_staging.dart

```

## This is where the data layers are constructed

`MealifyApp` is the only place in the repo that imports `meals_data`,
`drinks_data`, or `favorites_data`. It builds each repository and provides it
**as its interface**:

```dart
Provider<IMealsRepository>(
  create: (context) => MealsRepository(
    mealsDb: MealsDatabase(
      queryExecutor: queryExecutorFactory('mealify_meals_database'),
    ),
    mealDbApiClient: MealDbApiClient(httpClient: context.read<http.Client>()),
  ),
),
```

Because the provided type is `IMealsRepository`, a feature that reads it cannot
reach the concrete class even by accident. Each feature gets its own database file,
and one shared `http.Client` from
[`http_client_factory`](../../shared/http_client_factory) is provided above the
repositories that need it.

## Routing

`go_router` with `go_router_builder`, so routes are classes rather than strings.
A `StatefulShellRoute` gives the two tabs independent navigation stacks, and each
route builds a feature module:

```dart
class FavoriteDetailsRoute extends GoRouteData with $FavoriteDetailsRoute {
  const FavoriteDetailsRoute({required this.id});

  final String id;

  @override
  Widget build(BuildContext context, GoRouterState state) {
    return DeferredLoader(
      loader: favorite_details.loadLibrary,
      builder: (context) => favorite_details.FavoriteDetailsModule(
        id: id,
        favoritesRepository: context.read(),
        mealsRepository: context.read(),
        drinksRepository: context.read(),
      ),
    );
  }
}
```

Three things are happening there, and each is a rule:

**Routes are split across files with `part`.** `routes.dart` holds the shell and
the deferred imports; `ideas_routes.dart` and `favorites_routes.dart` are `part`
files. `go_router_builder` needs one library to generate `$appRoutes`, so the
branches cannot be separate libraries.

**Every screen is deferred.** Feature code is imported with a `deferred as`
prefix and loaded on demand, which splits web bundles and enables Android dynamic
modules. [`DeferredLoader`](lib/app_router/deferred_loader.dart) runs the load in
`initState` and holds the future, so a rebuild does not restart it. Without that,
recreating the future on every `build` would restart the load and flash the
loading screen.

**Navigation is decided here.** Feature modules take callbacks. The ideas route
passes closures that call generated route classes:

```dart
onMealTapped: (meal) => MealDetailsRoute(id: meal.id).go(context),
```

The feature knows a meal was tapped; the app knows that means a route. This is
what lets a feature be reused in an app with an entirely different navigation
structure.

## Routes take ids and nothing else

`go_router` supports passing an `$extra` object to skip a loading state on
in-app navigation. This app does not use it. `$extra` is null on a cold-start deep
link and after a browser refresh, so a screen has to work from the id regardless,
and supporting both paths means one of them is rarely exercised.

## Code generation

```sh
dart run melos generate
```

Regenerates `routes.g.dart` from the `@TypedGoRoute` and
`@TypedStatefulShellRoute` annotations, along with every other generated file in
the repo. Run it from the repo root rather than `build_runner` here: this package
depends on the data packages' Drift output, so building it before them fails with
`AssetNotFoundException`.

Note that `analysis_options.yaml` here disables `public_member_api_docs`. The app
composes rather than exporting an API, so its members have no external consumers to
document.

`build.yaml` sets `go_router_builder`'s `duplicate_route_paths` to `error`, so two
routes resolving to the same path fail generation instead of silently shadowing
each other at runtime.
